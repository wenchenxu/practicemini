## 签署全量同步超时修复（api-fadada）

用户部署三个云函数后忘记上传 api-fadada 触发器，手动云端测试 `syncPendingSignTasks` 报 `ret=-3 system error`。

### 诊断
- system error = 平台层失败（非业务错误）。最大嫌疑：**函数超时**——原实现串行逐份调法大大（每份 0.3~1s），积压 100+ 份即撞 60s 超时被强杀。
- 快速区分部署崩溃 vs 超时：云端测试 `{action:'getEnvInfo'}`，正常返回=模块OK（超时）；同样 system error=部署问题，重新「上传并部署：所有文件」。
- 逐份提交设计：失败的运行不丢进度，已处理的合同都落库了。

### 修复（已完成）
syncPendingSignTasks 重写：
- **并发 8**（Promise.all 分批）+ **单次上限**（默认 100，payload.limit 手动最大 200）+ **40s 时间预算**（到点收工，剩余留给下次，保证 60s 内返回）
- **lastSyncedAt 升序轮转**：orderBy('esign.lastSyncedAt','asc')，未同步过的优先（缺字段排最前）；无变化也写 lastSyncedAt 让它排到队尾——防止"司机永远不签的卡住合同"饿死新合同
- 返回增加 processed/remaining/hint，方便手动分批清理
- 定时器路径（{} 空 payload）默认 100 份/天，增量场景足够；积压多天也能靠轮转逐日消化

### 用户操作步骤（已告知）
1. 重新部署 api-fadada（所有文件）
2. 云端测试反复跑 `{action:'syncPendingSignTasks', payload:{limit:200}}` 直到 remaining=0
3. 右键 api-fadada「上传触发器」（syncSignTasks 07:30，之前忘了）
4. 确认新版小程序前端是否已发版（影响入口同步/三色角标）

### 经验教训
- 云函数内做 N 次外部 API 调用的批处理任务，**必须**：并发化 + 单次上限 + 时间预算 + 可断点续跑（排序轮转），否则积压场景必超时。
- ret=-3 system error 排查顺序：先 getEnvInfo 排除部署崩溃 → 看函数日志确认超时。
