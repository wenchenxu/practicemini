## 飞书推送城市乱码问题 — 已修复（同日）
- 现象：合同推送显示 `城市：%E5%B9%BF%E5%B7%9E`（URL 编码的"广州"）。
- 根因链：某份历史合同的 cityName 被编码入库 → contract-detail 续约跳转 `encodeURIComponent(乱码值)` 造成双重编码 → contract-new onLoad 只解码一次 → 仍是乱码 → contractV2 原样入库 → 续约链路自我传播。前端两个合同页 onLoad 均有单次解码，正常入口没问题，问题只在"从被污染库记录发起续约"这条链。
- 修复（三层防御，4 个云函数）：
  1. `safeDecodeUrl()` 工具函数加入 vehicleOps/contractV2/contractOps/dailyReport（纯 ASCII + %XX 特征才解码，正常中文/车牌不受影响，已 8 用例验证）
  2. contractV2 入口对 cityName/branchName 解码后再入库/推送/渲染 DOCX（阻断传播源头）
  3. 三个推送函数的 notifyFeishu 显示层解码（兜底，覆盖读库路径如 swapVehicle）
  4. dailyReport 的 buildVehicleCityMap 解码（报告兜底）
- 新增 vehicleOps 后门 action `fixEncodedCityNames`：扫描并修复 contracts(cityName/branchName)/drivers(cityName)/vehicles(cityName/branchName) 的编码乱码存量数据，dryRun 默认 true 只读预检。用法：预检 `{action:'fixEncodedCityNames',payload:{}}`，执行加 `dryRun:false`。
- 注意：已签署的 PDF 文档里若已含乱码，清洗后可用 contractOps 的 `render` action 重渲染。
- 待用户：部署 4 个云函数 → 跑 fixEncodedCityNames 预检 → 执行 → 验证。
